Arrays and Pointers

Storing many values under one name, 0-based indexing and the off-by-one trap, the sizeof trick, the address-of and dereference operators, pointer arithmetic, array decay in functions, and 2D row-major storage

§1 · Why Arrays? Contiguous Memory

A single variable holds one value. An array holds many values of the same type under one name, laid out contiguously in memory — which is the fact everything else in this chapter follows from.

When you write int scores[30]; the compiler reserves 30 int-sized slots back to back, with no gaps. scores[0] sits at the array's base address; scores[1] is exactly sizeof(int) — 4 bytes on a typical machine — further along, and so on. That regular spacing is what makes an index a fast operation: the machine computes one address, it does not search.

Declaring an array is just naming the type, the identifier, and the count:

int    scores[30];   // 30 integers, 30 * 4 = 120 bytes
double temps[7];     // 7 doubles
char   letters[26];  // 26 characters

The size must be a compile-time constant in standard C — use #define N 30 so the same name drives the declaration and every loop over it. Initialization can be full, partial (the rest is zeroed for you), or size-inferred:

int primes[5] = {2, 3, 5, 7, 11};   // fully initialized
int zeros[100] = {0};                // all 100 elements -> 0
int partial[5] = {1, 2};             // = {1, 2, 0, 0, 0}
int auto_size[] = {10, 20, 30};      // size inferred = 3
The mental model: an array is one labelled shelf of identical boxes. The name is the shelf; the index is which box; the boxes are always the same size and always touching. Hold that picture — the demo below draws it literally.

The first element lives at the base address (here 0x1000); every next element is exactly sizeof(int) = 4 bytes further along, with nothing in between. That is why the machine can jump straight to any element with one multiply-and-add — address = base + i × 4 — instead of walking the array. It is also why the index starts at 0: element i is i steps from the base, and the base itself is 0 steps away.

§2 · Indexing, the sizeof Trick, and the Off-by-One Trap

Indices run from 0 to N−1. Step outside that range and C does not stop you — it is undefined behavior: the program may crash, print garbage, or silently corrupt other data. There are no runtime bounds checks.

Reading and writing elements is direct, and the last valid index is always one less than the count:

int arr[5] = {10, 20, 30, 40, 50};
printf("%d\n", arr[0]);   // 10 - first element
printf("%d\n", arr[4]);   // 50 - LAST element (index 4, not 5)
arr[2] = 99;              // modify the third element

You can recover the element count from the declaration with the sizeof trick — total bytes divided by one element's bytes:

int n = sizeof(arr) / sizeof(arr[0]);   // = 20 / 4 = 5
The trick only works on the real array. Once the array is passed to a function it decays to a pointer (§4), and sizeof then returns the pointer's size (8 bytes), not the array's — giving the wrong n. Use the trick only in the scope where the array was declared.

The single most common C bug lives in the loop bound — one wrong character reads past the end:

for (int i = 0; i <= n; i++) { ... }   // BUG: touches arr[n] - out of bounds
for (int i = 0; i <  n; i++) { ... }   // correct: last index is n-1
One question fixes it every time: what is the largest index this loop uses? With i < n the largest i that runs is n-1 — the last valid element. With i <= n it is n — one past the end.

§3 · Core Processing Patterns

Almost every array program is one of three tiny loops: accumulate a total, track a running best, or scan for a target. Learn these once and you will recognise them everywhere.

Sum and average — accumulate, then cast before dividing so the average is not truncated to an integer:

int sum = 0;
for (int i = 0; i < n; i++) sum += arr[i];
double avg = (double)sum / n;   // cast BEFORE dividing

Maximum / minimum — seed the tracker from the first element, never from 0:

int max = arr[0];               // a REAL member of the set
for (int i = 1; i < n; i++)
    if (arr[i] > max) max = arr[i];
Why seed from arr[0], not 0? If every value is negative, starting max = 0 reports 0 as the maximum — a value that is not even in the array. The first element is always a genuine candidate, so it is the safe starting guess.

Linear search — scan left to right, return the index or -1:

int found = -1;
for (int i = 0; i < n; i++)
    if (arr[i] == target) { found = i; break; }
// found >= 0 -> success at that index; found == -1 -> not present
Worked example — grade statistics in one pass: a single loop over {85, 92, 78, 95, 88} can carry sum, max and min together: sum ends at 438 (average 87.6), max rises to 95 at index 3, min drops to 78 at index 2. Three patterns, one traversal.

§4 · Pointers, and How Arrays Decay to Them

A pointer is a variable that stores a memory address. Two operators are the whole story: & takes the address of something, and * follows an address to the value it points at.

The address-of operator &x asks "where does x live?"; the dereference operator *p asks "what value is stored at the address in p?". Writing through *p changes the original variable:

int x = 42;
int *p = &x;         // p holds the ADDRESS of x
printf("%d\n", *p);  // *p -> the value at that address = 42
*p = 100;            // write THROUGH the pointer -> x becomes 100
OperatorMeaningExample
&xaddress-of x — where is it?p = &x
*pdereference p — what value is there?*p = 100

An array name, used in an expression, decays to a pointer to its first element — so arr and &arr[0] are the same address. This is the bridge between arrays and pointers:

int arr[5] = {10, 20, 30, 40, 50};
int *p = arr;         // arr decays to &arr[0]
p[1]     == arr[1]    // 20 - a pointer can be indexed like an array
*(p + 2) == arr[2]    // 30 - pointer arithmetic reaches the same place
The identity that ties it together: arr[i] is defined in C as *(arr + i). The subscript is just sugar for "start at the base, step i elements, dereference." And pointer arithmetic is scaled: p + 1 advances by sizeof(int) bytes, not one byte — the compiler multiplies by the element size automatically.

💡 What to notice As i grows, the arrow ▲ steps one box to the right each time, and the line at the bottom shows *(arr + i) landing on exactly the same value as arr[i]. The pointer never jumps by one byte — each +1 moves it a whole int forward, because pointer arithmetic is scaled by the element size. That single rule is what lets a pointer walk an array, and it is why arr[i] and *(arr+i) are two spellings of one operation.

§5 · Arrays as Function Parameters, and 2D Arrays

When you pass an array to a function it decays to a pointer — the function receives the address of the first element, not a copy. That has two consequences you must design around.

First, the function can modify the original array (there is no copy to protect it). Second, the function has lost the size — sizeof inside it measures the pointer, so you must pass the count n as a separate argument:

void print_array(int *arr, int n) {                 // int arr[] means the same thing
    for (int i = 0; i < n; i++) printf("%d ", arr[i]);
    printf("\n");
}
void scale_array(int *arr, int n, int factor) {
    for (int i = 0; i < n; i++) arr[i] *= factor;   // modifies the CALLER's array
}
// in main: n = sizeof(nums)/sizeof(nums[0]) works HERE, before decay
Two rules for array parameters: (1) always pass n alongside the array — sizeof cannot recover it after decay. (2) If the function must not change the array, mark the parameter const int *arr so the compiler enforces read-only.

A two-dimensional array is a grid, and it is stored in row-major order — the whole first row, then the whole second row, contiguously in memory:

int m[2][3] = {{1, 2, 3},
               {4, 5, 6}};
printf("%d\n", m[1][2]);   // 6 - row 1, column 2
// memory order: m[0][0] m[0][1] m[0][2] m[1][0] m[1][1] m[1][2]
for (int r = 0; r < 2; r++)
    for (int c = 0; c < 3; c++)
        printf("%3d ", m[r][c]);   // row by row
Row-major, in one sentence: the last index changes fastest. Walking m[r][c] with c in the inner loop visits memory in the exact order it is laid out — which is the cache-friendly way to traverse a grid.
