§1 · What is a program?

Think of a program as a list of instructions. A person writes the list in a language a human can read; then the computer follows the list, one instruction at a time, doing exactly what it says.

But there is a gap. The computer does not understand English — or any human-readable language. Deep inside, it only understands sequences of 1s and 0s: binary. Everything it does — showing text, playing a sound, adding two numbers — happens because some pattern of 1s and 0s is processed by the hardware. Something has to sit between the human and the machine and translate one into the other. What does that translating, and how, is the subject of this lecture.

Algorithm

An algorithm is a set of steps for solving a problem, written clearly enough that anyone — or anything, including a machine — can follow it without having to guess what you meant. It is like a recipe, or directions to a friend's house: if one step is unclear, the follower may do the wrong thing. Good algorithms leave nothing to interpretation.

For a set of steps to count as a real algorithm, it must have four properties:

PropertyQuestion it answersMeaning
DefinitenessIs each step exactly clear?Each step is precise — only one possible reading, no ambiguity.
FinitenessDoes it ever end?It stops after a limited, countable number of steps — it cannot run forever.
Input/OutputDoes it use data and produce a result?It takes input and produces output.
EffectivenessCan each step actually be done?Every step is genuinely carry-out-able — nothing impossible.

A valid algorithm — directions to the nearest ATM:

INPUT: starting room number · OUTPUT: route to the nearest ATM
1. Exit room, turn left into corridor · 2. Walk to the end (~30 steps) · 3. Take the staircase down · 4. Exit through the main door · 5. Turn right, walk 50 m · 6. The ATM is on the right — use it · 7. STOP

It passes all four: every step names an exact action and amount (definiteness); there are exactly seven steps ending in STOP (finiteness); the INPUT/OUTPUT lines are stated (input/output); and every step is something a real person can do (effectiveness). Compare two that fail: "turn left at the big tree" fails definiteness (which tree is "big"?), and "keep looking until you find it" fails finiteness (no guaranteed end).

Flowcharts

A flowchart draws the same steps as shapes joined by arrows, so you can see the path — including where it branches. Four shapes cover almost any beginner flowchart: an oval (start/end), a rectangle (an action), a diamond (a yes/no decision), and an arrow (direction of flow). A diamond can send execution down two paths, and an arrow can point backward to repeat earlier steps — forming a loop. An algorithm is not always a straight line from start to end.

§2 · Programming languages

The only thing the processor (the CPU) can actually carry out is binary machine code — long sequences of 1s and 0s, where each pattern triggers one tiny hardware operation. Nobody types that by hand; we write in a human-readable language, and software translates it into the binary the CPU needs.

High-level vs low-level

Languages sit on a scale from low-level (close to the machine) to high-level (close to how a human thinks):

Machine code → Assembly → C / C++ → Java / Go → Python
← harder to write · faster to run · less portable  ……  easier to write · slower to run · more portable →

C/C++, the language of this course, sits deliberately in the middle: high-level enough to write readable, structured programs (loops, functions, named variables), yet low-level enough that you still see and control exactly what the machine does with memory and performance. Most operating systems and performance-critical software are built on exactly this trade-off.

Compiled vs interpreted

There are two broad strategies for turning your code into something the CPU runs: compile it all at once beforehand, or interpret it line-by-line as it runs.

Compiled (C/C++)Interpreted (Python)
When translatedOnce, before it runsAt runtime, line by line
SpeedFast — machine code is already readySlower — translation overhead every run
Errors show upBefore running — the compiler catches themAt runtime — when that line executes

Write 100 million integers to memory and sum them: a C program ≈ 0.3 s, the same job in Python ≈ 15 s — roughly 50× slower. Both do the identical work; the C program was translated to machine code before it started, while Python re-translates every one of those 100 million additions as it goes. This is not a criticism of Python — it is simply the measurable cost of "translate as you go" versus "translate once, up front," and a large part of why this course teaches C/C++.

§3 · A brief history of C

WhenWhat happened
1972
Bell Labs		Dennis Ritchie designs C so the Unix operating system can be written in a portable language — the same source recompiled for different hardware, instead of rewritten per machine. Powerful enough to write an OS, yet portable.
1983
AT&T Bell Labs		Bjarne Stroustrup adds features for organizing large programs around objects, producing C++ — broadly "C plus extra tools." Almost everything you learn about C here applies directly to C++.
Today
2026		Every major OS kernel (Linux, Windows, macOS) is written in C; it is the standard for embedded systems (cars, appliances, medical devices); and the performance-critical cores of AI frameworks (TensorFlow, PyTorch) are C, even when you use them through Python. Learning C is learning the language underneath almost everything else.

§4 · The C/C++ toolchain

How does human-readable C source become something the CPU can run? Through a pipeline of four tools, each taking the previous tool's output as its own input. Play the trace and watch one file change shape at every stage.

hello.c → running program · the four toolchain stages

animated
💡 What to notice Each stage consumes the previous stage's output — .c → .i → .s → .o → executable — and the file is still plain text right up to the assembler; only from .o onward is it binary. In daily work one gcc command runs all four for you, but when something breaks the error message names which stage failed, and that tells you what kind of mistake you made.

Running it from the command line

gcc -Wall -std=c11 -o hello hello.c  # compile
./hello                   # run
PartMeaning
gccThe GNU Compiler Collection — typing this one name runs the entire four-stage pipeline for you.
-WallTurn on all warnings. A warning still compiles, but flags a suspicious line — treat warnings as seriously as errors.
-std=c11Use the C11 standard (2011) when checking your code — being explicit avoids surprises.
-o helloOutput file name. Leave it out and you get the default name a.out.
./helloA separate command that runs the executable. The ./ means "in the current folder."

§5 · Hello, world — anatomy & execution

The traditional first program prints a short greeting. It looks tiny, but every character has a job. Step through it and watch what each line does as the program runs.

Running hello.c, line by line

animated
Terminal · output
💡 What to notice Execution does not start at the top of the file — #include is handled before the program runs, and the very first thing that executes is the body of main. Only the printf line puts anything on the screen; the \n is what moves the cursor to a new line, and return 0 hands the operating system an exit code of 0 meaning "finished successfully." Compiling and running are two separate steps — a silent compile means success, not "nothing happened."

Line by line: #include <stdio.h> copies in the declarations for input/output functions like printf; int main(void) defines the entry point — the first thing that runs — returning an integer and taking no arguments; the braces { } bound its body; printf("...") prints text to standard output; return 0; ends main and reports success; and each ; marks the end of one statement.

Common escape sequences

An escape sequence is a two-character combination starting with \, used for a character you cannot simply type inside quotes:

SequenceMeaning
\nNewline
\tTab
\\Literal backslash
\"Literal double-quote
\0Null character

§6 · The edit–compile–run–debug cycle

Writing a program is almost never one shot. You repeat a short loop until the program does what you meant — expect to go around it many times, even as an expert.

The working rhythm of every programmer

animated
💡 What to notice The loop points backward: debugging sends you back to editing, not forward. Where a problem shows up tells you what kind it is — a compiler error stops the build, a runtime error crashes a program that built fine, and a logic error lets the program build and run and finish — it just gives the wrong answer. The compiler cannot catch a logic error, because nothing is grammatically wrong.
Error typeWhen you see itExample
Compiler errorDuring compilationMissing ;, undeclared variable
Runtime error / crashWhile runningDividing by zero
Logic errorRuns, but the output is wrongOff-by-one in a loop

Worked example — reading a compiler error

Forget the semicolon after the printf line:

printf("Hello, world!\n")  /* missing ; */
return 0;

The compiler reports:

hello.c:5:5: error: expected ';' before 'return'
  • hello.c — the file. 5:5 — the line and column where the compiler noticed the problem. error: — a hard error, not a warning; no executable is produced until it is fixed.
  • expected ';' before 'return' — it was reading along expecting a semicolon and ran straight into return instead.

The trap this teaches: the semicolon is missing at the end of line 4, but the error is reported on line 5. That is correct behaviour — the compiler cannot know a semicolon is missing until it reads past where it should have been and hits the next thing. The lesson: when you get a compiler error, also check the line immediately above the one reported — a large share of beginner errors (missing ;, }, or )) live one line earlier.

Chapter summary

  1. Algorithm — finite, definite, effective, with input/output. A flowchart is the same steps as a picture, and it can branch and loop.
  2. High-level vs low-level — C/C++ sits in the middle: readable enough to write real programs, close enough to the hardware to see what is happening.
  3. Compiled vs interpreted — C/C++ is compiled once, ahead of time, which is why it runs far faster (≈50× here) than an interpreted language on the same task.
  4. The toolchain — preprocessor → compiler → assembler → linker → executable. One gcc command runs all four.
  5. Hello world — #include, main, printf, \n, return 0: every character has a purpose.
  6. Edit–compile–run–debug — your normal rhythm; knowing whether a problem is a compiler, runtime, or logic error tells you where to look.
